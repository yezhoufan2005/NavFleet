# axe `incomplete` 桶的人工审阅流程

## 为什么需要人来看

无障碍门禁（`e2e/specs/console-accessibility.spec.ts` + `support/axe.ts`）断言的是 axe 的
**violations** 桶里 serious / critical 为空。axe 的结果其实分四桶：

- **violations** —— 确定违规。门禁在管。
- **passes** —— 确定通过。
- **inapplicable** —— 规则不适用（页面上没有该类元素）。
- **incomplete** —— **axe 自己判不了**。

`incomplete` 是这份流程存在的原因。它最常见的来源是 `color-contrast`：当文字落在**半透明、
渐变或有元素叠加**的背景上时，axe 算不出「有效背景色」，于是既不敢判违规、也不敢判通过，
把它扔进 incomplete。Phase 10 已确认：**这类缺陷自动化 suite 抓不到** —— 断言它为违规会误伤
（很多其实达标），断言它通过则等于橡皮图章。所以唯一诚实的做法是：定期把整桶摆到人面前，
让每一条得到一个人的判定，而不是无人问津地累积。

## 什么时候跑

不是 CI 门禁（跑它的 spec 在 CI 里整体 `test.skip`，零耗时、从不拦），而是一个**按需**动作。
建议在这些时机各跑一次：

- 改动了表面 token、渐变/叠加层、半透明背景（`semantic.css` / 各卡片与遮罩样式）之后；
- 新增了一类会把文字画在图像/地图/渐变上的界面；
- 每次发版前的收尾核对。

## 怎么跑

```bash
npm run axe:incomplete
```

它起 e2e 的后端 + console dev server，用登录态遍历每个控制台界面（明暗两套主题、1440 宽），
收集 `incomplete` 桶，写一份合并报告到：

```
playwright-report/axe-incomplete.md
```

同一份内容也打到 stdout。**空清单是好结果**，不是出错。

> 宽度只取 1440：incomplete 桶由表面构成（叠加/渐变/透明度）驱动，不像 reflow 类问题那样随
> 视口变化，所以一个代表性宽度即可覆盖每个不同表面，同时把耗时压住。明暗都跑，因为半透明
> 叠加在两套主题下压出的有效背景不同。

## 怎么判定每一条

报告每行给出：规则、影响级别、出现的界面、元素选择器。逐条这样处理：

1. 在浏览器里打开那个界面，用开发者工具选中该元素。
2. **量一次有效对比度**：取文字色与它**实际压在其上的**背景色（把半透明层与其下方色叠加后
   的结果，不是 token 名义值），算对比度（devtools 的对比度取色器或任一 WCAG 对比度工具）。
3. 判定：
   - **达标（≥ 4.5:1，大字 ≥ 3:1）** → 记为已复核。若它反复出现且确定安全，可在
     `support/axe.ts` 留一行注释说明这个表面为何总是达标，免得下次又当新情况查。
   - **不达标** → 这是一个真缺陷，按普通无障碍缺陷修（调 token / 加不透明底 / 去掉渐变叠加），
     修完它会从 violations 桶冒出来或从 incomplete 消失。

关键是：**incomplete 不等于安全，也不等于违规 —— 它等于「还没有人看过」。** 这份流程把
「没人看过」变成「看过了，结论是 X」。

## 与门禁的关系

这份流程不改门禁，也不该改：把 incomplete 强行断言进 CI 只会得到 Phase 10 已经排除过的两种
坏结果（误伤或橡皮图章）。门禁继续只管 violations 的 serious/critical；incomplete 由这份按需
流程兜底。
