# 角色任务流与竞品 IA 调研（Phase 11B）

配套 [frontend-parity.md](frontend-parity.md)：那份说"现在有什么"，这份说"这些东西该为谁、以什么结构
组织"。两份都是 Phase 11C（IA 设计）的输入。

**方法**：任务流的"当前步数"逐条对着代码数过，不是估的，可回溯到 parity 清单的对应条目；竞品部分只
记录能查到明确出处的设计规则，来源列在文末。

## 0. 一句话结论

三条调研发现直接改变了我原先的 IA 假设：

1. **"地图占满主屏"可能是错的。** 仓储机器人车队的公开设计经验是：把每台车的实时坐标全铺出来是**厂商
   默认做法**，而管四十台以上的主管**第一周之内就不再看那个画面了**。有效的做法是主屏只留 4-5 个关键
   信号 + "现在需要你处理的那 3-4 台车"。→ 与 ROADMAP 里"态势 = 地图升为页面主体"直接冲突，11C 必须
   重新取舍。
2. **导航层级有现成的量化标准。** Grafana 把 IA 的 1-3 级放进主导航，第 4 级用 tab，第 5 级往下用页内
   标题/步骤器。这给了"分几个区、每区多深"一个可执行的判据，而不是凭感觉。
3. **大屏值班模式与我们现在的鉴权机制冲突。** 墙面看板的硬规则是"不可交互 + 不能有会话超时"，而
   NavFleet 是 15 分钟 access token + 静默刷新，且刷新是 fire-and-forget（[parity 9.23](frontend-parity.md)）。
   → 大屏不是"再做一个页面"，它需要一套专门的凭据方案。

## 1. 六类角色的核心任务流

步数口径：**从打开应用到拿到答案/完成动作的用户操作次数**（点击、输入、切页各算一步；等待不算）。
"做不到"表示当前实现无法完成该任务，不是步数多。

## 2. 竞品 IA 调研

只记录查到明确出处的设计规则，来源见文末。**不抄形态，抄的是判据。**

### 2.1 Grafana —— 导航层级有量化标准

这是本轮最可直接落地的一条。Grafana 的设计系统（Saga）对导航给出的是**规则**而不是范例：

| 规则                                         | 内容                                                                                                         | 对 NavFleet 的用法                                                                           |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------- |
| **层级与控件的对应**                         | IA 的 **1-3 级**放进主导航（megamenu）；**第 4 级用 tab**；**第 5 级及以下**用页内标题、步骤器等 inline 元素 | 直接采纳为 11C 的硬约束。它把"分几个区、每区多深"从审美问题变成可判定问题                    |
| 三种导航状态                                 | opened（覆盖层）/ closed / **docked**（窄视口下响应式收起）                                                  | 大屏与平板都需要 docked 态，不能只做一种                                                     |
| **每个分类区都要有落地页**                   | 不允许用重定向代替缺失的落地页                                                                               | 我们如果分出「管理」这类聚合区，就得给它一个真页面，不能点了直接跳到第一个子项               |
| 图标只给 1 级                                | 2 级以下不用图标                                                                                             | 减少视觉噪音                                                                                 |
| 标签用**名词**而非动词，句首大写             | —                                                                                                            | 现有 4 项（实时监控 / 历史回放 / 告警中心 / 设置）里「历史回放」是动词短语，可考虑改「历史」 |
| 面包屑由页面层级**自动生成**，不反映浏览历史 | 且必须与 IA 一致                                                                                             | 我们现在完全没有面包屑；分区变多后需要                                                       |
| 跨分支跳转要给"返回上一处"                   | 链接把用户送到 IA 另一个分支时提供返回                                                                       | 从告警中心跳到设备详情属于跨分支，需要这个                                                   |

Grafana 的告警侧另有一条经验值得记：他们把告警规则页做成**分页 + 强筛选 + 保存的搜索**，因为规则数量
会长到成千上万；而 Grafana 官方最佳实践里明确写了"基础设施类告警通常很吵，更适合放进看板/告警列表这类
**非呼叫**通道，而不是当作 paging 信号"。→ 对我们的启示：Phase 16D 的外发必须分级，不能所有告警一律推送。

### 2.2 Datadog —— 侧栏按"实际使用频率"分区

| 规则                     | 内容                                                                                                                                                                     | 对 NavFleet 的用法                                                           |
| ------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| 侧栏三段                 | 顶部：搜索 + **最近访问过的页面**（含具体的看板/监控项，不只是功能页）；中部：核心产品域，各自 hover 展开子菜单；底部：底层能力（Metrics / Logs）→ 协作工具 → 管理与支持 | NavFleet 规模小得多，但"最近访问"对"回到我刚才看的那台车"很有用              |
| **最常用的放最上和最下** | 排序依据是使用数据，不是产品结构                                                                                                                                         | 底部是第二个黄金位，别只当作"设置的垃圾桶"                                   |
| 深层级用 hover 子菜单    | 而不是多级展开                                                                                                                                                           | 我们层级浅，可能不需要                                                       |
| 收藏项要留足字符宽度     | 因为"看板或笔记本的名字通常比功能页长得多"                                                                                                                               | 若做"收藏这台车/这个编队"，宽度要按设备名规划                                |
| 改版目标                 | 对比度与可访问性、间距与可读性、**层级按真实工作流而非产品结构组织**                                                                                                     | 最后一句是原则性的：不要按"我们有哪些数据"分区，按"谁在什么时候要做什么"分区 |

### 2.3 仓储 / AGV 机器人车队 —— 一条与我们计划冲突的经验

这一节最重要，因为它**反对**我原先的方案。

| 发现                                       | 内容                                                                                                                                         |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------- |
| **实时坐标全铺是厂商默认做法，而且没人看** | 公开的仓储机器人看板设计经验：把每台机器人的实时坐标都铺出来是厂商的默认做法，而管理**四十台以上**的主管**在第一周之内就停止阅读那个画面**了 |
| 主屏只留 4-5 个关键信号                    | 有效的做法是把主屏收到 4-5 个信号，其余按需展开                                                                                              |
| 主屏应回答"现在该管哪几台"                 | 浮出**需要立刻处理的那 3-4 台车**，而不是穷举全部位置                                                                                        |
| 告警要有**差异化视觉权重**                 | 字重、颜色、屏幕位置、**声音**共同区分"必须马上处理"与"可以等"                                                                               |
| 处置动作要**内联**                         | 恢复流程放在同一屏，而不是把主管甩到厂商的另一个工具里                                                                                       |
| 角色视图不同                               | "早上 6 点打开的班组长要的是车队就绪度，而同一个看板对车间经理来说要的是本周吞吐达成"                                                        |

**与 NavFleet 现状和计划的三处冲突，需要你在 11C 拍板：**

1. ROADMAP 写的「**态势：全屏地图为主体**」与"没人看实时坐标画面"冲突。我倾向的折中：**总览页**主屏
   给 4-5 个信号 + "需要处理的车"列表，地图作为**独立分区**供确实要看空间关系时进入（找车、看编队
   聚集、看路网覆盖）——而不是让地图占据默认首屏。
2. 我们的**规模不同**：这条经验的前提是 40+ 台，NavFleet 目前示范 6 台、目标"几十到数百台"。6 台时
   地图完全看得过来，200 台时就是上面描述的情形。→ 结论是 IA 必须**随规模退化得体**，而不是二选一。
3. "**声音**"这一维我们完全没有。critical 告警在无人值守的值班室需要它，但浏览器自动播放策略要求
   一次用户交互才能解锁 —— 这是个真实的实现约束，得在设计里留位置（例如登录后一次"启用声音提醒"）。

### 2.4 大屏 / 墙面看板 —— 与我们鉴权机制的硬冲突

| 规则                       | 内容                                                                           |
| -------------------------- | ------------------------------------------------------------------------------ |
| **不可交互**               | 不需要点击、不需要滚动                                                         |
| **不能有会话超时**         | 必须支持无限期显示而不被登录打断                                               |
| 低信息密度 + 大字号        | 按"隔着房间能读懂"设计                                                         |
| 高对比度配色               | —                                                                              |
| 自动定时刷新               | 无需人工干预                                                                   |
| 去掉浏览器外壳与菜单、光标 | 保持画面干净                                                                   |
| 多看板轮播                 | 支持在若干看板之间循环                                                         |
| 设计者的自检问题           | "**有人在两米外、两秒内能看懂什么？**"——因为做这个页面的人永远只在一尺外看过它 |

物理侧还有两条会影响排版的：视距决定可读的最小字号与像素间距；显示墙底边通常离地约 1.2m（坐姿视线
高度），也就是**画面下部三分之一容易被前排设备遮挡**，重要内容不该放最下面。

**与 NavFleet 的冲突（必须解决，不是可选）**：我们是 15 分钟 access token + 7 天 refresh，而且刷新是
fire-and-forget、失败时不做任何事（[parity 9.23](frontend-parity.md)）。一块挂了三个月的屏，会在某次
refresh 静默失败后停在一个永不更新的画面上，**而且看不出来它停了**。所以 Phase 17C 的大屏模式需要：

- 专用的 kiosk 凭据（长期有效 + 只读权限 + 审计可辨识），**不做匿名开放**
- 画面上必须有"数据新鲜度"指示（最后更新时刻 + 陈旧超阈值就变色），否则"屏幕卡住"无法被发现
- 刷新失败要能自愈（重登或显式报错），不能静默

### 2.5 车队管理 SaaS 的通用模式

搜索结果里可复用的共识（原文 403 无法直接引用细节，只记可交叉验证的部分）：分层的 KPI 结构（顶层
少量总览指标 → 下钻到明细）、按角色区分视图、紧凑的趋势指示器（数字旁一条 sparkline 而不是单独一张
图）、红黄绿三色状态、以及移动优先的响应式。前三条与 2.1-2.3 相互印证，第四条我们要落到"平板 + 大屏"
两端而非手机。

## 3. 带进 11C 的结论

### 3.1 直接采纳为约束

| #   | 约束                                                                                            | 来源                       |

| C1  | IA 的 1-3 级进主导航，第 4 级用 tab，第 5 级往下 inline。**分区数量与深度按这条判定，不凭感觉** | Grafana                    |
| C2  | 每个聚合分区必须有真的落地页，不允许重定向到第一个子项                                          | Grafana                    |
| C3  | 导航标签用名词；面包屑由层级自动生成；跨分支跳转给"返回上一处"                                  | Grafana                    |
| C4  | 分区依据是"谁在什么时候要做什么"，不是"我们有哪些数据"                                          | Datadog                    |
| C5  | 主屏收敛到 4-5 个关键信号 + "现在需要处理的那几台车"                                            | AGV 车队                   |
| C6  | 告警靠字重 / 颜色 / 位置 / 声音四维区分紧急度，处置动作内联                                     | AGV 车队                   |

### 3.2 需要你在 11C 拍板的三件事

1. **地图的地位。** 现有计划是"态势 = 全屏地图为主体"，而调研说 40+ 台时没人看那个画面。我倾向：
   总览为默认首屏（4-5 信号 + 待处理车辆），地图降为独立分区。**这是对 ROADMAP 已写方案的修正建议。**
2. **规模退化策略。** 6 台与 200 台的最优 IA 不同。是做一套随规模自适应的（例如车辆数超阈值时列表
   默认折叠、地图默认聚合），还是明确只优化其中一端？
3. **声音提醒要不要做。** 值班室无人时它是刚需，但需要一次用户交互解锁自动播放，且会引入"静音/音量/
   免打扰时段"一串配置。

### 3.3 本轮调研否掉的两个我原先的想法

- ~~"地图升为页面主体是显然的升级"~~ —— 有公开经验直接反对，见 2.3。
- ~~"大屏模式就是再做一个宽屏页面"~~ —— 它的难点在凭据与新鲜度可见性，不在布局，见 2.4。
