## 1. 先减掉两个分区

ROADMAP 11C 列了七个候选分区（总览 / 态势 / 设备详情 / 告警中心 / 报表 / 管理 / 大屏）。盘点之后有两个
应该拿掉，理由与"地图放哪"无关，所以三个候选都照此收敛：

| 拿掉的       | 理由                                                                                                                                                                  |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **大屏**     | 它不是一个分区，是一种**模式**。硬规则要求它不可交互、无会话超时（C7），所以它是独立入口 `/wall` + kiosk 凭据，**不进主导航** —— 值班时没人会"导航到大屏"。           |
| **设备详情** | 它不是一级项，是 `/devices/:id` 这个**详情路由**，从列表、地图、告警任何地方都能进。把它提到一级是按"我们有设备这种数据"分区，违反 C4（按谁在什么时候要做什么分区）。 |

顺带一个必须做的合并：**历史回放不是页面，是设备详情的一个 tab**。现在它是独立页，代价是工程师查完实时
还要在历史页**重新选一次设备** —— 这正是那条「6 步且拿不到答案」的排故流程的一半。

设置页同样拆开：主题等个人偏好进用户菜单，连接诊断进「管理 / 系统状态」。

## 2. 三个候选

线框见 [frontend-ia-options.html](frontend-ia-options.html)，这里只记结论。

|       | 候选                         | 落地页                | 一级项                           | 判断       |
| ----- | ---------------------------- | --------------------- | -------------------------------- | ---------- |
| **A** | 地图为主体（现状直系升级）   | 全幅地图              | 态势 / 告警 / 历史 / 报表 / 管理 | 与 C5 冲突 |
| **B** | 总览为默认，地图降为分区     | 4–5 信号 + 待处理车辆 | 总览 / 设备 / 告警 / 报表 / 管理 | **推荐**   |
| **C** | 总览与态势并列，落地页可配置 | 用户自选              | 六个一级项                       | 不建议     |

**A 的问题不是"不好看"，是主屏答错了问题** —— 它答「大家都在哪」，而值班调度员要的是「现在该管哪几台」。
调研里那条经验很直接：管四十台以上的主管**第一周之内就不再看实时坐标画面**了。

**C 的问题是把决策转移给了每一个使用者。** "可配置默认页"通常是"没做决定"的代名词；两个高度相似的一级项
会持续制造「我该去哪个」的犹豫，而它并没有比 B 多解决任何一项任务流。

**B 的代价要说清楚**：与现状差异最大，四个页面全部重排，且总览是**新页面没有现成实现可搬**。收益是
13 项「做不到」里有 9 项在这个骨架下有了落点，排故从 6 步压到 2 步。

### B 的完整层级

```
L1  总览              /                默认落地
L1  设备              /devices         列表 ⇄ 地图（同一集合的两个投影）
L2    设备详情        /devices/:id
L3      实时 · 曲线 · 历史回放 · 告警史                （tab，第 4 级）
L1  告警              /alerts
L2    实时 · 历史 · 统计 · 规则                        （tab）
L1  报表              /reports
L1  管理              /admin
L2    用户 · 用户组 · 审计 · 设备接入 · 场景 · 报码字典 · 系统状态
—   大屏              /wall            不在导航内，kiosk 凭据
```

符合 C1（1–3 级进主导航、第 4 级用 tab）。`管理` 是聚合区，按 C2 需要一个**真的落地页**，不允许点了
直接跳到第一个子项。

## 3. 三项跨候选的设计

### 3.1 导航模型：左侧栏三态 + 细顶栏

侧栏展开 / 收起 / 覆盖三态；顶栏只放面包屑、车队选择、会话、实时状态点。

选侧栏而非顶栏导航的理由是具体的：**16:9 屏上垂直像素比水平稀缺**，而地图与 ECharts 曲线吃的正是高度。
顶栏导航要占掉 56–64px 通高，侧栏收起后只占 44px 通宽。

面包屑按 C3 由页面层级自动生成（现在完全没有面包屑，分区变多后需要）；跨分支跳转（告警 → 设备详情）
给"返回上一处"。

### 3.2 URL：建议从 hash 迁到 web history

现在是 `createWebHashHistory()`，原因写在 `router/index.ts:1-8`：nginx 没有 `try_files`，前端镜像也没有
自定义 conf。

迁移的收益是刚需而非美观：

- Phase 16D 的告警外发要「点通知链接直达那一条告警」
- 告警中心的筛选状态**现在完全不进 URL**（parity 6 节），刷新即回默认，也没法把一个筛选视图发给同事

代价明确，且**必须现在定**（属于部署改动，不能等 Phase 14）：

1. `frontend/Dockerfile` 加一份 nginx conf，含 `try_files $uri /index.html`
2. 边缘 `deploy/nginx/locations.conf` 的 `location /` 同步
3. 两者的安全响应头要一并带上（`add_header` 不跨 location 继承）

### 3.3 断点：两端是平板与大屏，不是手机

现状是四个凭手感加的断点（1560 / 1320 / 1240 / 860）。改为一条刻度，与 Tailwind 默认对齐并补两档：

| 档     | 宽度 | 场景     |
| ------ | ---- | -------- |
| `md`   | 768  | 平板竖屏 |
| `lg`   | 1024 | 平板横屏 |
| `xl`   | 1280 | 笔记本   |
| `2xl`  | 1536 | 桌面     |
| `3xl`  | 1920 | 值班台   |
| `wall` | 2560 | 墙面看板 |

现在的 axe 审计只跑过 **1440×900 一个视口**；新前端要把 1024 与 2560 纳进去。

## 4. 大屏值班模式：难点在凭据与"看不出屏幕卡住了"

| 墙面看板的硬规则           | NavFleet 现状的冲突                                                                                                                                          |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 不能有会话超时             | 15 分钟 access token + 静默刷新，而刷新是 fire-and-forget、失败时不做任何事（parity 9.23）→ 一块挂三个月的屏会在某次刷新静默失败后停住，**而且看不出它停了** |
| 不可交互、无光标无菜单     | 需要一套专门的只读渲染路径，不能复用带侧栏的外壳                                                                                                             |
| 大字号、高对比、隔房间可读 | 自检问题：**有人在两米外、两秒内能看懂什么？**                                                                                                               |
| 物理约束                   | 显示墙底边通常离地约 1.2m（坐姿视线高度），画面下部三分之一容易被前排设备遮挡 —— 重要内容不放最下面                                                          |

因此 `/wall` 需要：kiosk 凭据（长期有效 + 只读 + 审计可辨识，**不做匿名开放**）、画面上的**数据新鲜度
指示**（最后更新时刻 + 超阈值变色，否则"屏幕卡住"无法被发现）、刷新失败能自愈或显式报错。

### 5.1 规模阈值为什么是 40 而不是我先前说的 24

先前那个 24 是**估的**，没有依据；负责人要求"按现实需求取值"，那就得给出取值理由：

- 调研里唯一一个实测数字是 **40**：管四十台以上的主管**第一周之内就不再看实时坐标画面**。这是整份
  调研中唯一能支撑阈值的经验值，与其自造一个数字，不如用它。
- 演示车队 6 台、目标"几十到数百"，所以阈值必须落在这两端之间且靠近"地图开始失效"的那一侧。
- 列表侧不构成约束：`largeFleet` 实测 200 台挂载 34.5ms / 更新 17.4ms、500 台 85.3ms / 43.5ms，
  列表在目标规模内都不是瓶颈。**决定阈值的是地图的可扫读性，不是列表的性能。**

**一个把阈值风险降到很低的设计**：用户显式切换过视图之后，这个选择被记住并**优先于自动判定**。
也就是说阈值只决定**第一次进入**时看到哪个视图 —— 猜错的代价是一次点击，不是长期难用。
（沿用 `navfleet:map-mode` 已有的持久化思路，但要注意它现在的白名单只有 `gps`/`scene`，
需要扩展为"列表 / 地图 + 自动"三态。）

### 5.2 web history 的部署工作项（Phase 12B 必须一起做）

1. `frontend/Dockerfile` 增加一份 nginx conf，含 `try_files $uri $uri/ /index.html`
2. 边缘 `deploy/nginx/locations.conf` 的 `location /` 同步同一 fallback
3. **两处都要带上安全响应头** —— `add_header` 不跨 location 继承，现在全套头只挂在 SPA 那一个 location 上
4. compose 实跑验证：直接访问 `/devices/xxx` 与刷新都不能 404
5. `e2e` 的 `baseURL` 与断言不受影响（现有 17 例走的是点击导航而非直接输 URL），但**新增深链接用例**

### 5.3 声音提醒的设计要点

- **解锁**：浏览器自动播放策略要求先有一次用户交互。登录成功后放一个一次性的"启用声音提醒"动作
  （而不是弹窗轰炸），解锁状态记在本地。
- **只给 critical**：预警与提示不出声，否则值班室会把音量关掉 —— 那等于这个功能不存在。
- **配套配置**：静音开关、音量、免打扰时段。三项都进个人偏好（用户菜单），不进管理页。
- **可发现性**：未解锁时在告警区域给一条低干扰提示，说明"当前不会响"，而不是静默地不响。
- **与大屏的关系**：`/wall` 的 kiosk 会话同样需要解锁，但它不可交互 —— 所以解锁要么由布屏时的一次
  操作完成，要么该屏放弃声音、只靠视觉。这一点留到 Phase 17C 定。
